 ### HASH Function

| Point                | Detail                                                       |
| -------------------- | ------------------------------------------------------------ |
| **Not encryption**   | No key involved; **one-way** function                        |
| **Input → Output**   | Any size input → **fixed-size digest**                       |
| **Irreversible**     | Computationally impossible to go from output back to input   |
| **Avalanche Effect** | Even **1-bit change** in input → completely different output |
     **Example**; `T` (01010100) vs `U` (01010101) differ by 1 bit, but their MD5/SHA1/SHA-256 hashes are entirely different.

##### Key Properties ( Stepwise )
```
Step 1: Take any input (file, password, text) of any size
    ↓
Step 2: Run through hash function (MD5, SHA1, SHA-256, etc.)
    ↓
Step 3: Get fixed-size output (digest/hash)
    ↓
Step 4: Output is encoded (hexadecimal or base64) for readability
```


#### Hashing Collision 

| Concept                  | Explanation                                               |
| ------------------------ | --------------------------------------------------------- |
| **Definition**           | Two different inputs produce the **same hash output**     |
| **Why it happens**       | **Pigeonhole effect** — unlimited inputs, limited outputs |
| **Good hash function**   | Makes collision probability **negligible**                |
| **Engineered collision** | Attacker intentionally creates a collision                |
     **MD5 & SHA1 are BROKEN** — collisions can be engineered. Never use for passwords or sensitive data. Use **SHA-256** or higher.

  ## Real-world Cybersecurity Context 
   **Password Storage**
```
   User enters password
        ↓
Server hashes it → compares with stored hash
        ↓
Match? Grant access : Deny access
```
- Server never stores the actual password only the *hash.*
- Even if database leaks, attackers get hashes, not passwords.
  
#####  Other Security Uses 

| Use Case                 | How Hashing Helps                                        |
| ------------------------ | -------------------------------------------------------- |
| **Data Integrity**       | Verify files/downloads haven't been tampered (checksums) |
| **Digital Signatures**   | Hash a document, then sign the hash (faster & secure)    |
| **Malware Detection**    | Compare file hashes against known malware databases      |
| **TLS/SSL Certificates** | Verify authenticity of websites                          |
| **Forensics**            | Prove evidence hasn't been altered                       |



### Insecure Password Storage for Authentication 
***Authentication vs Password Managers***

| Authentication                    | Password Manager                        |
| --------------------------------- | --------------------------------------- |
| Only needs to **verify** password | Must **retrieve** password in plaintext |
| Hashing works perfectly           | Hashing won't work (needs encryption)   |

##### Three Insecure Practices ( Stepwise )
```
┌─────────────────────────────────────────────────────────┐
│  PRACTICE 1: Storing Passwords in PLAINTEXT            │
│  → Anyone with DB access sees passwords directly        │
│  → Example: RockYou breach — 14M+ passwords leaked      │
│  → Result: rockyou.txt wordlist on Kali Linux           │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  PRACTICE 2: Using DEPRECATED ENCRYPTION                │
│  → Passwords encrypted but can be decrypted             │
│  → Example: Adobe breach — used old encryption format   │
│  → Password hints stored in plaintext (sometimes = pass)  │
│  → Result: Passwords retrieved relatively quickly       │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  PRACTICE 3: Using INSECURE HASH + NO SALT              │
│  → Weak hash algorithm (e.g., SHA-1)                     │
│  → No salt = same password = same hash (rainbow tables) │
│  → Example: LinkedIn 2012 breach — SHA-1, no salting   │
└─────────────────────────────────────────────────────────┘
```

**Key-Terms**

| Term               | Definition                                                     |
| ------------------ | -------------------------------------------------------------- |
| **Plaintext**      | Password stored as-is, readable by anyone                      |
| **Encryption**     | Reversible — can decrypt back to original                      |
| **Hashing**        | One-way — cannot reverse to original                           |
| **Salt**           | Random value added before hashing to prevent same-hash attacks |
| **Rainbow Tables** | Precomputed hash lists to crack unsalted passwords             |
